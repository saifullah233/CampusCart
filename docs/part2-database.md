# CampusCart Backend — Part 2: Database Architecture + Flyway

**Date:** 2026-08-09
**Scope:** Persistence foundation — conventions, base auditing, UUID strategy, and the
first five reference/identity entities with their Flyway migrations.
**Builds on:** Part 1 skeleton (unchanged). No marketplace domains (product, cart, order,
payment, chat, admin) are implemented here.

---

## 1. Conventions

| Concern | Decision |
|---|---|
| Table names | `snake_case`, **plural** (`users`, `cities`, …). Plural also sidesteps the reserved word `user`. |
| Column names | `snake_case`, singular. |
| Primary key | `id` — UUID generated by the app (`GenerationType.UUID`), stored as **`BINARY(16)`**. |
| Auditing | Every table has `created_at`, `updated_at` (`DATETIME(6)`, UTC), and `version` (`BIGINT`). |
| Optimistic locking | `version` via JPA `@Version` on all entities (through `BaseEntity`). |
| Foreign keys | Column `<ref>_id`; constraint `fk_<table>_<ref>`; `ON DELETE/UPDATE RESTRICT`. |
| Unique constraints | Named `uq_<table>_<cols>`. |
| Secondary indexes | Named `idx_<table>_<cols>`; **every FK column is indexed**. |
| Engine / charset | InnoDB, `utf8mb4` / `utf8mb4_unicode_ci`. |
| Timestamps in Java | `java.time.Instant`; Hibernate `jdbc.time_zone=UTC`. |

**Schema ownership:** Flyway owns the schema. Hibernate runs with
`ddl-auto=validate` — it never creates or alters tables; it only fails fast if an entity
mapping drifts from the migrated schema.

### UUID storage rationale
`BINARY(16)` over `CHAR(36)`: ~55% smaller keys, smaller/faster B-tree indexes, less
FK-index bloat. Trade-off: raw values aren't human-readable in SQL — use
`BIN_TO_UUID(id)` / `UUID_TO_BIN(?)` when querying by hand.

## 2. ER Diagram (text)

```
                 ┌───────────────────────┐
                 │        cities         │
                 │ id (PK, BINARY16)     │
                 │ name                  │
                 │ state                 │
                 │ UQ(name, state)       │
                 └───────────┬───────────┘
                             │ 1
                             │
                             │ N        city_id → cities.id
                 ┌───────────┴───────────┐
                 │       colleges        │
                 │ id (PK)               │
                 │ name                  │
                 │ city_id (FK)          │
                 │ UQ(name, city_id)     │
                 └───┬───────────────┬───┘
              1      │               │ 1
                     │               │
      college_id     │ N             │ N   college_id → colleges.id
      → colleges.id  │               │
      ┌──────────────┴───────┐   ┌───┴────────────────────────┐
      │        users         │   │   college_email_domains     │
      │ id (PK)              │   │ id (PK)                     │
      │ email  UQ           │   │ domain  UQ (global)         │
      │ full_name           │   │ college_id (FK)             │
      │ college_id (FK)     │   └─────────────────────────────┘
      └─────────────────────┘

   ┌───────────────────────┐
   │      categories       │   (standalone reference data, flat)
   │ id (PK)               │
   │ name  UQ              │
   │ slug  UQ              │
   └───────────────────────┘
```

**Relationships**
- `cities (1) ──< colleges (N)` — a college is in exactly one city.
- `colleges (1) ──< users (N)` — a user belongs to exactly one college.
- `colleges (1) ──< college_email_domains (N)` — a college owns one or more email
  domains; each domain resolves to exactly one college (`domain` is globally unique).
- `categories` — standalone; flat taxonomy for now.

## 3. Tables

### `cities`
Shared geographic reference data.

| Column | Type | Notes |
|---|---|---|
| id | BINARY(16) | PK |
| name | VARCHAR(120) | NOT NULL |
| state | VARCHAR(120) | NOT NULL — part of uniqueness so it must be present |
| created_at / updated_at | DATETIME(6) | audit |
| version | BIGINT | optimistic lock |

Unique: `uq_cities_name_state (name, state)`.

### `colleges`
| Column | Type | Notes |
|---|---|---|
| id | BINARY(16) | PK |
| name | VARCHAR(200) | NOT NULL |
| city_id | BINARY(16) | FK → cities.id, NOT NULL |
| created_at / updated_at | DATETIME(6) | audit |
| version | BIGINT | |

Unique: `uq_colleges_name_city (name, city_id)`. FK: `fk_colleges_city`.
Index: `idx_colleges_city_id (city_id)`.

### `college_email_domains`
| Column | Type | Notes |
|---|---|---|
| id | BINARY(16) | PK |
| domain | VARCHAR(255) | NOT NULL, globally unique |
| college_id | BINARY(16) | FK → colleges.id, NOT NULL |
| created_at / updated_at | DATETIME(6) | audit |
| version | BIGINT | |

Unique: `uq_college_email_domains_domain (domain)`. FK:
`fk_college_email_domains_college`. Index: `idx_college_email_domains_college_id`.

### `users`
Core student identity only. Auth columns (`password_hash`, `email_verified`, `role`,
`status`) are **deliberately deferred** to the auth module's own migration.

| Column | Type | Notes |
|---|---|---|
| id | BINARY(16) | PK |
| email | VARCHAR(255) | NOT NULL, unique |
| full_name | VARCHAR(150) | NOT NULL |
| college_id | BINARY(16) | FK → colleges.id, NOT NULL |
| created_at / updated_at | DATETIME(6) | audit |
| version | BIGINT | |

Unique: `uq_users_email (email)`. FK: `fk_users_college`. Index:
`idx_users_college_id`.

### `categories`
Flat product taxonomy (standalone in Part 2).

| Column | Type | Notes |
|---|---|---|
| id | BINARY(16) | PK |
| name | VARCHAR(120) | NOT NULL, unique |
| slug | VARCHAR(140) | NOT NULL, unique (URL-safe identifier) |
| created_at / updated_at | DATETIME(6) | audit |
| version | BIGINT | |

Unique: `uq_categories_name (name)`, `uq_categories_slug (slug)`.

## 4. Index Strategy

- **Primary keys** are the clustered index (InnoDB) on `id`.
- **Every foreign key column** has a dedicated secondary index so joins and referential
  integrity checks don't table-scan. Where a composite unique constraint's leading
  column is *not* the FK (e.g. `colleges (name, city_id)`), a separate FK index is added
  (`idx_colleges_city_id`) because the composite cannot serve `city_id`-only lookups.
- **Unique constraints** double as lookup indexes: `users.email`, `categories.slug` /
  `categories.name`, `college_email_domains.domain` support the natural read paths
  (login by email, category by slug, domain→college resolution) with no extra index.
- No speculative indexes were added; they arrive with the queries that need them.

## 5. Flyway Migrations

| Version | File | Contents |
|---|---|---|
| V1 | `V1__geo_and_institutions.sql` | `cities`, `colleges`, `college_email_domains` (+ FKs, indexes) |
| V2 | `V2__users.sql` | `users` (+ FK to colleges, unique email) |
| V3 | `V3__categories.sql` | `categories` (flat) |

Location: `src/main/resources/db/migration`. **Applied migrations are immutable** — all
future schema changes go into new `V4+` files. Backward compatibility is preserved:
these are purely additive `CREATE TABLE` migrations.

## 7. Deliberately Out of Scope (Part 2)

- Product, Cart, Order, Payment, Chat, Admin domains — untouched.
- Product's future `product_type` and `selling_reach` dimensions — **noted for a later
  part**, not modeled here.
- Auth columns on `users` — added later via a new migration.
- The old product "visibility model" — not recreated.
- Category hierarchy — omitted (flat); can be added later via a nullable `parent_id`.
