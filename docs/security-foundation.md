# CampusCart Security Foundation

**Part:** 3, common infrastructure and security foundation  
**Date:** 2026-08-09

This document describes the reusable security boundary used by the Part 4 authentication
flows. Product, Cart, Order, and provider-specific email/SMS integrations remain out of
scope.

## Request Security

- The application is stateless. Spring Security does not create HTTP sessions.
- CSRF is disabled for the bearer-token API because authentication is sent in the
  `Authorization` header rather than an ambient browser cookie.
- `JwtAuthenticationFilter` accepts only a bearer access token and places an
  `AuthenticatedUser` in the `SecurityContext` after signature, issuer, expiry, subject,
  email, and role validation.
- Public routes are explicitly limited to liveness, health, OpenAPI/Swagger, `OPTIONS`
  preflight requests, and the framework error route. All other routes require authentication.
- `/api/v1/admin/**` additionally requires `ROLE_ADMIN`; method-level policies use
  `@PreAuthorize` with the same server-assigned role authorities.
- `/api/v1/auth/**` and `/api/v1/otp/**` are public because they establish or rotate
  credentials; they validate all input and return only standard envelopes.
- Filter-chain failures use the same `ApiResponse` and `ApiError` envelope as MVC failures.
  They return generic 401/403 messages and never include exception details or stack traces.
- Invalid path/query parameter conversions are normalized to a `MALFORMED_REQUEST` response,
  not a stack trace or generic 500.

## Access Tokens

`JwtService` creates signed HS256 access tokens with:

- `iss`: configured issuer;
- `sub`: the server-assigned user UUID;
- `email`: the user email needed by the principal;
- `role`: the server-assigned role;
- `iat` and `exp`: timestamps derived from the injected UTC `Clock`.

Access tokens are short-lived by default (`15m`). The signing secret is required through
`JWT_SECRET`, must be at least 32 characters, and has no source-controlled fallback. Parser
failures are intentionally indistinguishable to clients.

The JWT filter does not log bearer values or parser details. Existing access tokens remain
valid until expiry; refresh issuance and rotation re-check account status, so suspended or
unverified users cannot obtain new credentials.

## Refresh Tokens

Refresh tokens are opaque, high-entropy values generated by `SecureRandomTokens`.
`RefreshTokenService` stores only a SHA-256 digest in `refresh_tokens`, never the raw value.
The table keeps expiry, revocation, and replacement lineage with an FK to `users`.

Rotation is transactional and row-locked:

1. Hash the presented raw token and lock its database row.
2. Reject missing, unknown, expired, revoked, or inactive-account tokens with the same
   generic `InvalidTokenException`.
3. Persist a new opaque token and return its raw value to the caller.
4. Revoke the presented row and record the replacement id.

If a revoked token is replayed, all remaining active refresh tokens for that user are
revoked. This is deliberately conservative and limits the value of a stolen token chain.
`deleteExpired()` is available for a later scheduled cleanup job; no cleanup scheduler or
refresh endpoint is exposed yet.

## Credentials And Roles

- `PasswordEncoder` is a BCrypt encoder for the future password-authentication adapter.
- `CampusCartUserDetailsService` is a database-backed lookup and prevents Spring Boot from
  creating/logging a generated default user. It does not expose a login endpoint yet.
- New `User` instances default to `STUDENT` and `PENDING_VERIFICATION`.
- Role, status, email verification, and password-hash changes use server-side domain
  methods. There is no public role setter and no request DTO binds directly to the entity.
- Controllers must derive ownership from `@AuthenticationPrincipal AuthenticatedUser.id()`
  or a service-level current-user abstraction. A request body or path parameter must never
  be treated as proof of ownership.
- Credential login is protected by `login_rate_limits`, which stores only a SHA-256 hash of
  the normalized email lookup key. By default, five failed attempts in fifteen minutes lock
  that key for fifteen minutes and return `LOGIN_RATE_LIMITED`.

## CORS

CORS is configured from `security.cors.allowed-origins` and defaults to the two local
development frontend origins. Origins are explicit; wildcard origins are rejected, and
credentials are disabled because the API uses bearer headers. Deployments should set
`CORS_ALLOWED_ORIGINS` to the exact trusted frontend origins.

## Configuration

Required runtime variables include the database password and JWT signing secret:

```text
DB_PASSWORD=<database password>
JWT_SECRET=<random value with at least 32 characters>
```

Optional variables include `JWT_ISSUER`, `JWT_ACCESS_TOKEN_TTL`,
`JWT_REFRESH_TOKEN_TTL`, `LOGIN_MAX_FAILURES`, `LOGIN_RATE_WINDOW`, `LOGIN_LOCKOUT`,
and `CORS_ALLOWED_ORIGINS`. Docker Compose fails fast when `JWT_SECRET` is absent. No
secret belongs in `application.yml`, Dockerfiles, source files, or committed `.env` files.

Redis is present in Compose only as optional local infrastructure for future modules. The
current backend does not connect to Redis; OTP and login abuse protection are database
backed. Compose binds database and Redis ports to `127.0.0.1` for local development.

## Verification

The security foundation is covered by `mvn test` with a real MySQL 8 Testcontainer:

- fixed-clock JWT creation, expiry, and tamper rejection;
- context startup and Flyway migrations through V5;
- public liveness and configured CORS preflight;
- standard JSON 401 and 403 responses;
- JWT principal reconstruction and method/URL role authorization;
- refresh-token hashing, rotation, and replay revocation.

The Part 4 flow is documented in `docs/authentication.md`. Provider-specific email/SMS
transport still requires a deployment adapter for `OtpDeliveryGateway`; the default
gateway publishes a transient in-process event and never logs the code.
